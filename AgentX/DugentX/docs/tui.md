# 编码 TUI

一个跑在终端里的 DugentX 界面：模型流式吐字你一个字一个字看得见，工具调用是一行行记录，
写文件会把 diff 画出来，审批弹在屏幕中间等你按一个键。

它最值得说的不是「好看」，而是它是**长出来的**：加这个界面没有改循环、没有改工具管道、
没有给审批加分支。全部接口只有一个——提供一个 `ctx.human`。

界面本身建在 **textual** 上，而 textual 是一个**可选依赖**（`pyproject.toml` 里的
`tui = ["textual>=8.2.8"]`）。不装它只会少一层界面，不会少一次执行——理由见
下面「诚实的边界」。

---

## 怎么启动

```bash
# 1. 装界面。textual 是可选依赖，不装的话交互模式起不来
uv sync --extra tui

# 2. 真跑。默认读 dugentx.tui.yml，不是 dugentx.yml
export DEEPSEEK_API_KEY=sk-...
uv run dugentx tui

# 3. 想看它读的是哪份配置，就明说。命令行给的 -c 永远优先
uv run dugentx -c dugentx.tui.yml tui

# 4. 一个 key 也不要：回放适配器。模型是假的，工具、权限、diff、日志全是真的
uv run python examples/tui_demo.py

# 5. 脚本化：跑一个回合就退出，不进输入界面
uv run dugentx tui --once "看看这个目录里有什么"
```

**为什么 `dugentx tui` 不读 `dugentx.yml`。** 原因写在 `dugentx/cli.py` 的 `_config_for` 里：
如果按全局默认去读 `dugentx.yml`，那份配置里**没有 tui 插件**——于是最自然的命令会得到
一句「这次组合里没有 tui 插件」。这不是安全边界，是纯粹的绊脚石。TUI 和 `run` / `chat`
用的不是同一份组合（前者要装界面和它的画师，后者不要），所以默认值按子命令分开：
`dugentx tui` 用 `TUI_CONFIG = "dugentx.tui.yml"`。`-c` / `--config` 给了就用给的；
`dugentx.tui.yml` 不存在时才退回 `dugentx.yml`。

如果这次组合里确实没有 tui（比如你指明了 `-c dugentx.yml`），它会把缺的那一行说出来，
退出码 2：

```
dugentx: 这次组合（...）里没有 tui 插件。
把它加进配置就能长出来：

  - id: tui
    plugin: dugentx.plugins.tui

或者直接用仓库里那份：uv run dugentx -c dugentx.tui.yml tui
```

启动之前你自己能判断的两件事：

| 需要 | 为什么 |
|---|---|
| 一个能跑工具的模型 key（或回放适配器） | TUI 只是界面，它不产生能力 |
| 真的终端（不是管道、不是重定向） | 不是 TTY 时它会说一句话然后以退出码 2 结束，而不是挂住 |

`--once` 走的是另一条路：不用终端、不用 textual，输出是一行行纯文本。退出码有意分三档：
0 正常跑完，1 这个回合炸了，2 起不来。

## 它长什么样

真终端里 `dugentx tui` 跑一个回合（`examples/tui_demo.py` 跑出来的真输出，所以它
和 `--once` 那条路一个字都一样——排版是同一份）：

```
DugentX
  model=deepseek-flash  session=dcbf492c  tools=10
  cwd=...\DugentX
• 把 demo-note.txt 里的状态改成完成
── step 0
▸ 我先读一下这个文件。

╭─ read_file  examples/workspace/demo-note.txt
· read_file(path='examples/workspace/demo-note.txt')（只读，直接放行）
│ ✓ read_file
│   examples/workspace/demo-note.txt（共 2 行，显示 1-2）
│   1	# 演示用的一行笔记
│   2	状态：待办
── step 1
▸ 读到了，是一行待办。我把它改成完成状态。

╭─ edit_file  examples/workspace/demo-note.txt  old=状态：待办  new=状态：完成
同意：edit_file(path='examples/workspace/demo-note.txt', old='状态：待办', new='状态：完成')
│ ✓ edit_file
│   已在 examples/workspace/demo-note.txt 里替换 1 处
--- examples/workspace/demo-note.txt
+++ examples/workspace/demo-note.txt
@@ -1,2 +1,2 @@
 # 演示用的一行笔记
-状态：待办
+状态：完成
── step 2
▸ 改完了。diff 在上面——你看到的就是这个 TUI 存在的理由。

── turn completed  steps=3  tools=2  tokens=0
```

屏幕最下面那一行是状态条（它不属于流水账，所以上面这段里没有它）。空闲时和
干活时，它是这两行：

```
· deepseek-flash  session=9a40a380  steps=0  tokens=0  权限=dangerous→confirm、network→confirm、read→auto、write→confirm、其他→confirm
⠼ 4.2s  deepseek-flash  session=9a40a380  steps=1  tokens=0  权限=dangerous→confirm、network→confirm、read→auto、write→confirm、其他→confirm
```

前面那个字符就是整行状态：`·` 是空闲，`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` 在转就是有活干，
后面跟着的是**这一回合已经跑了多久**。它只在回合真的在跑的时候转（回合开始
起转、`turn/end` 停下、界面退场停表），所以「它在动」和「有事情在发生」永远
是同一件事。（`animate: false` 时它退化成一个静止的 `⠿`，也不读秒。）

输入框的占位提示是 `› 说点什么，或者 /help`（`› ` 是配置里的 `prompt`）。

几个细节，都是刻意的：

- **开场三行**（`formatting.banner_lines`）：`model` 是循环真正会用的那个模型名
  （`ctx.models.current().describe()`，读不到就退回 `agent.config.model`）；`session` 只取
  会话 id 的末 8 位——完整 id 是给日志用的，屏幕上够区分两个会话就行；`tools` 是这次装进来
  的工具件数（`len(ctx.tools.names())`）；`cwd` 是 `fs` 缝的 `root`。
- **`── step N` 不是装饰**。它对应循环里的一次模型请求，让你知道现在花掉了几步。状态条上的
  `steps` 说的是**这个回合**走到了哪一步，所以每个回合开始时会被重置。
- **一次工具调用是一张卡**：`╭─` 是顶边，下面每一行都以 `│` 起头，所以「这几行属于同一次
  调用」不用数缩进就看得出来。卡里第一行是结果（`✓` / `✗` / `⊘`），后面是被折叠过的输出。
  没有底边：一张卡结束的信号就是下一条 `╭─`，再加一行只有符号的 `╰─` 只是噪声。
- **diff 不套进卡里**。它自己带 `+` / `-` / `@@` 这些行首标记，而 `formatting.classify()`
  正是按它们判语气的；再套一层 `│` 会把那套标记挤到第二位，上色和折叠跟着一起失效。
- **只读工具直接放行**（`· …（只读，直接放行）`），要问的那一档才停下来问。这不是 TUI 的规则，
  是 `permissions` 缝的规则——TUI 只是在它决定放行或不放行的时候，把那一句显示出来。
- **`同意：…` 那一行是审批的结果**（`permission/decided`），后面跟着被问的那个调用本身。
  屏幕上没有痕迹的话，事后没人说得清当时到底同意了哪一条。
- **工具输出会折叠**：头 6 行 + 尾 4 行，中间写「…（省略 N 行）…」；单行超过 200 字符也会截断，
  并写明还有多少字符没显示。被截断而不说，读起来和完整的一样真，那比不截断更糟。
- **diff 不是从工具输出里解析的**。原因见下面「画师为什么挂在 post-execute 上」。
- **`tokens=0`** 是回放适配器如实报告的结果：没有真的调用，就没有开销。它没有编一个数出来；
  真跑时这里的 `tokens` 是**这个会话累计**的数，从会话日志算出来，不是事件里那一轮的数。

### 字形表

屏幕上的每一个符号都有且只有一个意思。它们是排版的一部分（纯文本那条路照样有，
所以管道里、日志里也读得出来），和颜色无关——颜色是界面的事，字形不是。

| 字形 | 意思 | 出现在 |
|---|---|---|
| `•` | 人说的话 | 输入的回声 |
| `▸` | 助手的正文 | 流式吐出来的那些字 |
| `◦` | 人对一次提问的回答 | 审批/问答的回显 |
| `?` | 一次提问 | 问题本身那一行（选项还是 `[y]` `[a]` `[n]`） |
| `╭─` | 工具卡的顶边 | 每次工具调用 |
| `│` | 工具卡的正文边 | 结果行和它的输出 |
| `✓` | 成功 | 工具结果、状态 |
| `✗` | 失败、出错 | 工具结果、错误行 |
| `⊘` | 被拦下（**没执行**，是策略说不跑） | 工具结果 |
| `!` | 警告 | 旁白里的 warn |
| `──` | 一步、一个回合的边界 | `── step N`、`── turn …` |
| `·` | 低声旁白；状态条空闲 | 只读放行、状态条 |
| `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` | 正在干活（只在状态条上转，非交互那条路不会出现） | 状态条 |
| `⠿` | 正在干活，但不许有动画（`animate: false`） | 状态条 |
| `›` | 候选列表里高亮的那一条 | 输入框上面的补全提示 |

这套字形和 `dugentx/cli.py` 里那份事件回显（`· step`、`✓/⊘/✗`、`?`、`⚙`）是同一套，
因为它们是同一件事在两个地方。`⊘` 和 `✗` 只差一个字形，所以被拦下的那一行会多写
一个词（`⊘ read_file（被拦下）`）：这两种的后果不一样——一个要去改策略，一个要去改代码——
不该让人去背字形表。

### 状态条：事实归事件，时间归钟

状态条上的**事实**（模型、会话、步数、累计 tokens、权限档位）只被事件推着更新，
**没有定时器**：`model/switched`、`llm/usage`、`step/start`、`turn/end` 各自带着自己
那半截事实来。一个每 200 毫秒重画一次的状态条，会让你分不清「它变了」和「它只是又刷了
一下」。

但「这一步已经跑了 4.2 秒」不是编的——它是一个**钟**的事实。所以状态条上有一个定时器，
它的权力被限死：只在回合真的在跑的那段时间里转（`paint.py` 用 `turn/start` /
`turn/end` 开关，见 `StatusUpdate.busy`），回合结束就停、界面退场就停（`StatusBar.on_unmount`，
不停的话一个还在跑的定时器会把进程吊住）。两句话而不是一句：**事实归事件，时间归钟。**

权限那一项是 `ctx.permissions.describe()` 的输出（按标签名排序，末尾是没有标签的工具算哪一档）；
读不到就不写这一项——空着比编一个「默认」诚实。界面刚起来的那一帧不会有任何事件来告诉它这些
事实，所以它自己先读一次（`_seed_status`）。

### 一次亮相

新的一条助手正文开始写的时候，它会从半亮升到全亮（0.22 秒的透明度动画）。整个界面
**只有这一处动效**——动效的作用是「这里刚发生了一件事」，超过这个量级它自己就成了要等的东西。
已经写完的行进的是 `RichLog`（一行行都是写完的），为它们逐行做动画要另写一套渲染，
换来的只是好看一点。

（实现上动的是 `styles.opacity` 而不是 `widget.animate("opacity", ...)`：textual 8 里
`Widget.opacity` 是一个算出来的只读属性，那种写法会在动画第一帧抛异常——而它抛在异步的
动画循环里，界面会在动效中途炸掉。理由写在 `app.py` 的 `_reveal` 里。）

## 它是怎么加上去的

### 一句话

> 加这个 TUI 只做了一件事：**提供一个 `ctx.human`。**

### 为什么这件事需要一个新缝

原来的审批自己去读 stdin。这在「终端问答」下没问题，但界面一换成 TUI 就断了：
TUI 有自己的输入框、自己的键位、自己的重绘节奏，它不可能让审批去调 `input()`——
那会立刻和在重绘的界面打架。

把问题拆开就清楚了。「要不要问」和「怎么问」是两件事：

```
permissions 缝  ──依赖──▶  human 缝  ◀──实现──  stdio 通道（plugins/human.py）
（决定要不要问）           （只负责问）          TUI    通道（plugins/tui.py）
```

于是 `human` 成了第 12 条缝。它的词汇很小：问一句（`ask`）、选一个（`choose`）、
单向告知（`note`）。`dugentx/tui/app.py` 里的 `TextualHuman` 就是这条缝在 TUI 上的实现
（`name = "tui"`），行为刻意和 stdio 通道一致，只是长得不一样。

### 改了什么

`permissions` 的审批走 `ChannelApproval`（`dugentx.yml` 里 `permissions` 那一行的 `mode: channel`
就是它），它**按需**取通道——审批不去 `inject` 通道，而是在真要问的那一刻才去要
（`ctx.get("human")`）。这样换通道不产生装载顺序问题，「同一份配置换个界面」就真的只是换个界面。

界面这一侧新增的全部内容，是 `ctx.human` 的一个实现、一个 textual 应用、一个订阅事件的画师。

### 没改什么

| 没动的东西 | 为什么不用动 |
|---|---|
| 循环（`agent_loop_basic.py`） | TUI 不接管 `agent.send`。回合还是循环在跑，它只是观察者 + 输入源 |
| 工具管道（`seams/tools.py`） | 画师挂在已有的 `tools/pre-execute` / `tools/post-execute` 上 |
| 内核（`kernel/`） | 新缝用的是和别的缝完全一样的机制 |
| 审批逻辑 | 它只多了一个「问谁」的分支，问什么、什么时候问一个字没变 |

### 整份配置

`dugentx.tui.yml` 的全部内容：

```yaml
extends: dugentx.yml

patch:
  - id: human
    disabled: true          # 不再用 stdio 通道
  - id: tui
    plugin: dugentx.plugins.tui
    config:
      prompt: "› "          # 输入框的占位提示前缀，不改变任何行为
      show_banner: true
      history_limit: 200    # 记住多少条历史输入（↑ / ↓ 翻），只在内存里
      animate: true         # 状态条的转圈和秒表；false 就是静止的 ⠿
```

`human` 那行必须关掉，因为两个通道提供**同一个服务键**（`ctx.human`），
一个进程里只能有一个。这不是限制而是设计：同时有两张嘴问同一个人，只会把问题问乱。
想换回最朴素的终端问答，把这两条 patch 删掉即可。

`prompt` / `show_banner` / `history_limit` / `animate` 就是 `tui` 插件认得的所有键——写别的会装载失败，
报错会告诉你可用的有哪几个。

`animate: false` 关掉状态条上那个转圈和秒表（改成静止的 `⠿`，也不读秒）。会动的东西在有些场合
是干扰（录屏、回放），而「我正在干活」这件事不需要靠动来说。非交互那条路本来就一条动画也没有
——它连状态条都没有。

### 包里的八个文件

```
dugentx/tui/
  __init__.py      包的门面：导出命令表、排版函数、纯文本那条路。**故意不 import textual**
  formatting.py    纯排版：一件事该长成哪几行（字形、diff、折叠、状态行、语气判定、转圈的帧）
  commands.py      `/` 命令表与解析：is_command / split / help_lines / unknown_lines / 补全
  fuzzy.py         名字的模糊匹配：补全提示和 provider 选择器共用一套「像不像」（纯函数）
  paint.py         订阅事件，把事件翻译成排版调用（两条路共用）+ 快照
  plain.py         不依赖 textual 的那条路：PlainTui / PlainHuman / TuiConfig / is_tty
  widgets.py       状态条 StatusBar、补全提示 SuggestionPopup、provider 选择器、审批弹窗
  app.py           textual 应用 TuiApp、`ctx.human` 的实现 TextualHuman
```

**为什么排版（`formatting.py`）和事件翻译（`paint.py`）要单独两层。** 它们都不认识 textual，
所以交互界面（`app.py`）和非交互输出（`--once`、CI、`examples/tui_demo.py`）用的是同一份排版、
同一个画师；差别只在渲染调用最后落到哪儿（`paint.py` 里的 `RenderSwitch`：装载时指向纯文本，
界面真的起来时转过去，退场时转回来）。分叉的代价很具体：界面上折叠成 10 行、管道里全画出来的话，
「你看到的」和「你脚本里拿到的」就成了两件不同的事。

`commands.py` 是纯数据，`help_lines()` 读它、命令面板读它、派发也读它——一个只有派发代码认识、
而帮助里没写的命令，等于不存在。补全的候选也读它（`arg_source` 说明哪条命令的参数能补、
补哪一类名字），所以「有哪些命令、哪条要参数」只有一个出处。

**为什么补全的判断放在 `commands.py` / `fuzzy.py` 而不是界面里。** 那两个文件不认识 textual，
于是「打 `prv` 找不找得到 `/provider`」「接受之后这一行变成什么」都是能脱离终端被检查的纯函数；
界面只剩「把候选画出来、把键接上」。反过来写，这套判断就只能靠一个跑起来的终端来验。

### 画师为什么挂在 post-execute 上

结果和 diff 不在 `tool/result`（那是个 `emit`，**同步**的）上画，而在
`tools/post-execute`（waterfall，会被 `await`）上：

```python
on("tools/pre-execute", self._on_before_tool, prepend=True)
on("tools/post-execute", self._on_after_tool)
```

两个理由：

1. 画 diff 要读文件，异步的读没法在同步的 `emit` 里被 await。
2. **顺序确定**：先出结果行，再出 diff。

`pre-execute` 上的监听器在工具执行**之前**拍一张文件快照（走 `ctx.fs.read_text`，不绕过那条缝），
`post-execute` 上再读一次对比。所以 diff 来自「执行前后真实读到的内容」，不是从工具输出里解析的
文本——工具输出是给模型看的，随时可能改写法；而这样拿到的永远是事实。只有
`write_file` / `edit_file` 会拍快照，名单和 `fs_tools.py` 真正注册的名字一致。

两个监听器都**必须调 `nxt()`**：画师是渲染层，它没有权力拦下或篡改任何一次调用——`post-execute`
上那个还得原样把 outcome 还回去，改了它就等于悄悄篡改了模型看到的东西。

### 换成 textual：买到了什么，付了什么

在这之前，界面这一层自己写终端：原始模式、按键解析、光标位置按显示列宽算（一个汉字占两列）。
那些现在归 textual。这笔交易的账要算清：

**买到的**：成熟输入框（光标、宽字符、翻历史都不用自己算）；一个可滚动的流水账
（`RichLog`，写完的行滚上去，正在写的那一行挂在另一个 `Static` 上，因为它要的是「替换最后一行」）；
弹窗与选择器；命令面板；上色（一张 `_STYLES` 表把语气映射到颜色，而「这一行是什么语气」由
`formatting.classify` 一处判定）。最实际的收益是**无头测试台**：`App.run_test()` + `Pilot`
让 `tests/test_tui_app.py` 在没有真终端的机器上断言「屏幕上看到了什么」——一个只能在真终端上
验一遍的界面，等于一个没验证过的界面。

**付出的**：多了一个第三方依赖（可选，但界面的存在以它为前提，「只用标准库」这条只对 harness
成立，不对这个界面成立）；纯文本那条路必须单独存在（`plain.py`），于是 `dugentx/tui/__init__.py`
和 `plugins/tui.py` 都不能在模块顶层 `import textual`——缺依赖时**换一个实现**（`PlainTui` 提供
同样的 `human` / `tui` 两个服务键），而不是抛一段 traceback。这也是为什么 `dugentx plugins` /
`dugentx run` 在一台没装 textual 的机器上照常能跑。

## 命令与键位

命令是**界面自己的**，不发给模型。这条区分是硬的：一句 `/clear` 被当成提示词发出去，模型会
一本正经地回答你它没法清屏——那种错很难查，因为一切看起来都在正常工作。不认识的 `/随便什么`
也不会悄悄变成用户的话，它会说「没有这条命令」并把认得的列出来。

`/help` 的全部输出：

```
命令（以 / 开头；它们由界面处理，不会发给模型）：
  /help — 列出这些命令和键位（F1）
  /status — 看模型、会话、步数、tokens、权限档位
  /model [名字] — 看当前模型；带名字就换（provider 不变）
  /provider [名字] — 打开 provider 选择器，也可以切回适配器（Ctrl-O）
  /clear — 清空屏幕上的流水账（会话日志不动）（Ctrl-L）
  /quit — 退出（Ctrl-Q），也可以写 /exit
键位：
  Ctrl+O — 换 provider / 模型
  Ctrl+L — 清屏
  Up — 上一条输入 / 上一条候选
  Down — 下一条输入 / 下一条候选
  Tab — 补全候选
  Enter — 接受候选
  Escape — 取消提问 / 收起补全
  Ctrl+D — 退出（输入框空的时候）
```

键位表不由 `/help` 手写，它读的是界面自己的 `BINDINGS`（这样说明和实际键位不会分叉）：

| 键 | 作用 | 说明 |
|---|---|---|
| `Ctrl+O` | 换 provider / 模型 | 打开选择器，等同于 `/provider` |
| `Ctrl+L` | 清屏 | 等同于 `/clear`，只清屏幕 |
| `↑` / `↓` | 上一条输入 / 上一条候选 | 补全提示开着的时候挪高亮，否则翻历史输入（最多 `history_limit` 条，只在内存里） |
| `Tab` | 补全 | 提示开着就接受高亮那条；提示关着而这一行有候选，就把提示叫出来。没候选时它**不是**界面的键（落回 textual 的挪焦点） |
| `Enter` | 接受候选 | 补的是**命令名**时顺手把这一行跑掉；补的是**参数**时只补，不跑。没候选时它还是「提交」 |
| `Escape` | 收起补全 / 取消提问 | 先收提示（一个字都不动输入框），没有提示时才去取消正在等的那一句回答 |
| `Ctrl+D` | 退出 | 输入框是空的时候才退出；里面有字就什么都不做 |
| `Ctrl+Q` | 退出 | textual 自带的绑定，界面没有覆盖它 |
| `Ctrl+P` | 命令面板 | textual 自带；里面每一条命令和手打一条走的是同一个 `_run_command` |

`Ctrl+D` 是带优先级的：输入框自己也想要这个键（删光标右边一个字符）。两个语义抢一个键，
只能选一个——按 `Ctrl+D` 的人多半是想退出，所以「退出」赢；想删右边一个字符，还有 `Delete` 键。

`Tab` 和 `Enter` 也是带优先级的（`Input` 上回车是「提交」，屏幕上 `Tab` 通常是「挪焦点」，
两个都比「接受候选」更早拿到键）。抢在前面之后，**平时必须把它们让回去**——靠的是
`TuiApp.check_action`：这一行没有候选的时候这两条绑定等于不存在，提交和挪焦点一切照旧。
一个永远生效的绑定会把回车吞掉，而回车是这台机器上最不能出错的那个键。

## 补全

打到 `/` 的那一刻，输入框上面就出现一张候选表——不用按任何键。这是**自然触发**：
`/` 是命令的起点，这件事不需要谁来告诉界面「补全该开始了」。

```
› /provider [名字]  打开 provider 选择器，也可以切回适配器
  /clear           清空屏幕上的流水账（会话日志不动）
  /quit            退出
  /exit            /quit 的别名：退出
```

每一行分两段：**这条命令的用法**（叫什么、要不要参数——行首那个 `[名字]` 就是
「它还欠一个参数」），和**一句说明**。两段都必要——光有名字，人还得去猜它是干什么的。
行首的 `›` 是高亮的那一条，而 `Tab` / `Enter` 接受的就是它；确认之后填进输入框的是
**命令名本身**，用法只出现在屏幕上。

几件要说清楚的事：

- **边打边收窄。** 打 `st` 只剩 `/status`；打 `prv` 也能找到 `/provider`（子序列匹配，
  用的是 provider 选择器那一套 `fuzzy_score`——两份「像不像」会长成两个不一样的答案）。
- **别名自己占一行。** 打 `ex` 看到的那一行是 `/exit`，说明里写它是 `/quit` 的别名。
- **提示会随终端高度缩放**，最多 8 行（`SuggestionPopup._limit`）；高亮跑到窗口外面时窗口
  跟着它走——一个「选中了第七条、屏幕上是前八条」的列表，看起来就像按了没反应。
- **打完就不提示了。** 输入框里那一段和某个候选一字不差的时候，候选**撤掉**。这不是为了
  省屏幕：提示开着的时候回车是「接受」，接受一个没有变化的值等于什么都没做，
  那条命令就再也跑不起来（按几次回车都一样）。这条是写测试时先撞上的，不是你猜的。
- **一行普通的话不会让提示冒出来。** 只有看起来还像命令（开头是 `/`）的时候才有候选。
- **不做路径补全。** pi 在 `Tab` 上做那件事，因为它的输入框里有 `@文件` 这种明确的标记，
  于是「这一段是不是一个路径」有答案。DugentX 的输入框收的是一句话，没有任何标记能说明
  某几个字是路径——猜出来的候选只会是一个半准的补全，而半准的补全比没有补全更耽误事。

### 参数的补全

打完命令名再打一个空格，如果这条命令有参数，候选就换成**那个参数能是什么**：

| 打什么 | 候选来自哪儿 |
|---|---|
| `/model <一半>` | `ctx.models.current().model`（现在在用的那个模型名） |
| `/provider <一半>` | `ctx.models.providers()` + `ctx.models.adapters()`——**和选择器列的一模一样** |

`/provider` 那一份必须和选择器同意：两份名单会长成两个「可选的东西」的答案，而人只会相信
屏幕上后来出现的那个（后出现的是选择器）。而且补进去的那个词是有作用的——`/provider mistral`
打开选择器时，过滤框里已经写着 `mistral`。补进一个被命令忽略的参数，比补不出来更容易让人
以为界面坏了。

`/model` 那份只有**一个**候选，而且故意不是 provider 名单：`/model` 干的事是「provider 不变、
换模型名」，往它后面填一个 provider 名，等于填了一个命令会当成模型名去用的值——补出来的
错值比补不出来糟。真正的模型名清单只有 any-llm 在发请求时才知道，界面列不出来，所以它不编
一个（这条也是 `commands._argument_items` 里那段注释说的）。

顺序也定了：命令的候选按命令表的顺序（「先看、再改、最后走」），参数的候选把**在用的那个**
放第一位。同分时保持这个顺序，不按字母排——因为第一条就是 `Tab` 会替你按下去的那条。

补全的**判断**（这一行能补什么、接受之后这一行变成什么）是纯函数，在 `commands.py` 和
`fuzzy.py` 里，一个 textual 都不认识：所以「打 `prv` 找不找得到 `/provider`」这件事，
不需要起一个终端就能被检查。

被提问时：

| 情况 | 形态 |
|---|---|
| 要一段自由文本（模型通过 `ask` 工具问人） | 用**输入框**问：问题写进流水账，占位提示换成问题原文，回车提交，`Escape` 等于没回答 |
| 要一个键（审批） | 弹一个**弹窗**（屏幕中央），三个按钮 `[y] 允许这一次`、`[a] 本会话内都允许`、`[n] 拒绝（默认）` |

审批的默认项是「拒绝」，焦点也落在它上面：**连按回车不会不小心把写操作放过去**，要放行就得
按对一个字母（字母键和按钮走的是同一条路，所以「按 y」和「点允许」不可能给出两种答案）。
误拒的代价是再敲一次，误允的代价不是。

`a` 的记住粒度值得说清楚：它记的是提问的**标题**，而审批传的标题就是**工具名**。所以对
`edit_file` 选过一次「本会话内都允许」之后，**这一个会话里所有** `edit_file`——不管改哪个文件、
改什么内容——都不再问了。粒度是工具级的，不是文件级的。想要更细的粒度（比如只放行某个目录），
那属于 `permissions` 缝的 `tool_overrides`，不该塞进界面里：界面记不住那么多上下文，也不该记。

`Escape` 取消一次审批，等于「没有人回答」，审批按拒绝处理（工具会收到一条被拦下的结果，
模型看得到，于是它有机会换个办法，而不是整个会话断掉）。

## 换 provider / 模型

三个入口，做的事一样：`/provider`、`Ctrl+O`、命令面板里的那一行。`/provider mistral`
多给了一样东西——**打开时过滤框里已经写着 `mistral`**（补全补进去的那个词因此是有作用的，
见上面「补全」那节）。

选择器是一个列表，分两段：

1. any-llm 认得的全部 provider 名（这台机器上是 52 个），离线就能列出来；
2. **已经注册在 `ctx.llm` 里的适配器**（比如 `replay`），上面有一行禁用的分隔标题
   「—— 已经注册的适配器（可以切回去）——」。

第二段就是「回得去」这件事的全部实现：没有它，一旦换成真 provider 就回不到离线模式了，
而那正是最需要能回去的时候。

过滤是**边打边做**的：打 `mi` 找得到 `mistral`，打 `ds` 也能找到 `deepseek`（子序列匹配，
最像的排前面）。选中一个 provider 之后还要再给一个模型名（占位提示 `模型名，例如 deepseek-chat`），
因为 **provider 和 model 缺一不可**：只换 provider 而不改模型名，会拿新家去请求旧家的模型，
报出来的错看着像「这家不支持这个模型」，其实是我们自己没把状态改干净。

**为什么界面要绕一层 `ctx.models`。** 因为只有 `dugentx/providers/llm_anyllm.py` 可以
`import any_llm`（`scripts/check_boundaries.py` 会在别的文件里 import 它时报错）。provider 名
就是从那一个文件里的 `available_providers()` 来的，由 `plugins/llm.py` 装到 `ModelSwitcher` 上，
界面只调 `ctx.models.providers()`。界面要是自己 import 一遍，「换 provider 不改代码」这句话
从第一个选择器开始就是假的。

真正动手的是 `dugentx/providers/model_switch.py`：`switch()` 注册新适配器、把默认切过去，并把
**所有记录当前模型的地方一起改掉**（`registry.default_model` 和循环会读的 `agent.config.model`）。
然后它记进会话日志、发 `model/switched` 事件，再通过 human 通道说一句——真跑时你会看到
`从 replay 换成 anthropic/claude-sonnet-4-20250514` 这样的旁白，状态条紧接着变成
`anthropic/claude-sonnet-4-20250514`。因为切模型这件事只有一份实现（在这一层，不在界面里），
一次切换只有一个答案的出处：`dugentx replay <会话 id>` 的日志里会多出一条
`model/switched   provider=... model=... adapter=...`。

`/model` 不带名字只看现在是谁；带名字就换，provider 不变。如果当前用的是回放适配器（它按脚本
吐字，没有 provider），它会说清楚该走哪条路——先 `/provider` 选一家，再换模型。

**一个诚实的后果。** 换到一个**key 没配**的 provider 会成功：`switch()` 不接触 key，适配器把
key 的解析留给 any-llm 在真正发请求时按 provider 自己的约定去找（`OPENAI_API_KEY` 之类）。
所以这次切换当场不会有任何抱怨，状态条也会改成新名字——失败出现在**下一个回合**。

弹窗里能当场显示的错误只有两种：模型名是空的（`模型名不能是空的`，界面自己判的），以及
`switch()` 抛出的 `PluginError`。错误写在弹窗里、弹窗不关，因为「这一件事没做成」不等于
「这个界面坏了」，改个名字再试一次就行。`Esc` 在选模型那一步退回列表，在列表上则整个取消，
什么都不改。

## 诚实的边界

**不是 TTY 就起不来界面。** `dugentx tui` 在管道、重定向或 CI 里会说一句话然后退出码 2：

```
dugentx: 这里不是交互式终端，界面起不来；脚本化请用 dugentx tui --once "..."
```

脚本那条路是 `--once`（走 `plain.py`）。非交互时审批**一律拒绝**，理由会写进决定里
（「…需要确认，但当前不是交互式环境；要无人值守地跑，就把这一档的答案写进配置」）。
这是有意的：在 CI 里挂住等一个永远不会来的按键，比当场说「不」糟糕得多。代价是——**在 CI 里
它会把该问的都拒掉**，那你不如用 `permissions` 的 `mode: policy`。

**textual 不在也能跑，只是没有界面。** 交互模式会打印唯一一句话，退出码 2：

```
dugentx: 这个 TUI 需要 textual，装一下就能用：uv sync --extra tui
```

`--once` 照样跑（纯文本），`dugentx run` / `dugentx plugins` 完全不欠界面任何东西。

**`/help` 里给 `/help` 记的等价值是 `F1`，但 textual 8.2.8 没有默认绑 F1。** 按 F1 不会有反应；
命令面板是 `Ctrl+P`。那一行是命令表里的说明文字，不是一条真的绑定。

**`/clear` 只清屏幕。** 会话日志一个字都不动——它是唯一真相，屏幕上这一份只是它的一个视图。
把「清屏」做成「删历史」的话，一次手滑就抹掉了当时到底问了谁、同意了哪一条。历史输入也一样：
它只在内存里（`history_limit` 条），进程退出就没了，真正的记录在 `.dugentx/sessions/*.jsonl`。

**补全只有命令和命令的参数，没有路径补全。** 理由在「补全」那一节：DugentX 的输入框收的是
一句话，里面没有任何标记能说明某几个字是路径。`@文件` 那种写法属于「以后要不要做」，
不做的话现在就不该有一个半准的路径补全在那儿猜。

**补全给的候选只有界面知道的那些名字。** `/model` 只补现在这个模型名（真实的模型名清单在
any-llm 那边，离线列不出来），`/provider` 补 provider 名和已注册的适配器名——和选择器同一份。
**不编一个列不出来的清单**：一个补进去却错的值，比补不出来糟。

**`↑`/`↓` 一个键两个意思，但不会同时需要。** 提示开着的时候挪高亮，否则翻历史输入。从历史里
翻出来的一行**不会**自己把提示叫出来（有意思要翻的那个键就翻不动了），想补它按 `Tab`。

**思考链不显示。** 流里带 `Delta.reasoning`（DeepSeek 默认开思考模式），现在故意不画它：
它是模型的自言自语，混进答案里会让人分不清哪句是结论。数据已经在事件里，想显示要另开一个开关，
而不是默认打开。

**不做语法高亮。** 代码块按原文显示（流水账是 `highlight=False` 的）。

**它不接管循环。** 回合还是 `agent.send` 在跑，界面只是观察者。所以「边跑边插话」
「跑的时候按 Esc 中断」这类事现在没有——`Escape` 只取消正在等的那一句回答，或者收起补全提示。
真要做，正确的位置是 `ctx.agentLoop`（它本身就是一个可替换的服务），而不是在这个界面里塞一个特例。

**相对路径按进程 cwd 解析。** 从别的目录启动 `dugentx tui`，它会以那个目录为工作区
（`cli.py` 传的是 `Path.cwd()`，`fs` 缝的 `root` 是 `.`）。这是 `fs` 缝的行为，TUI 只是没去覆盖它。

**`--once` 那条路没有状态条，也不上色，也没有一帧动画。** 状态条的收件人是显式的 `None`，
而不是一个什么都不做的方法——一个安静地不生效的方法，谁都不会发现它其实没生效。纯文本那条路
往管道、日志、CI 记录里写，往里面塞 ANSI 的后果是文件里多出一堆看不懂的字符，塞动画帧的后果
是日志里多出一堆没有信息的跳动。**字形会出现在那条路上**（它是排版），**动画不会**（它是界面）。
