# 写一条提交信息

先把改动读完（`git diff --staged`）再动笔。没读完就写，写出来的是猜测。

## 结构

第一行：`<类型>(<范围>): <做了什么>`，不超过 50 字，用祈使句——写「修好加载顺序」，不要写「修好了加载顺序」。

空一行，再写正文，回答三件事：

- **为什么改**：原来错在哪、缺什么。这是三个月后唯一还有人需要的信息。
- **怎么改**：只写不显然的部分；代码里一眼能看懂的不重复一遍。
- **影响面**：破坏性变更、要一起改的配置、还没解决的部分。

## 避免

- 一条提交里塞两件不相关的事——拆不开，说明你其实做了两个决定。
- 「修复 bug」「优化代码」这种不含信息的描述。
- 把变量名和行号写进去：它们会变，提交信息不会。
