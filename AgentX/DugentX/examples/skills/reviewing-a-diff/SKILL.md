# 审一段 diff

先读提交信息和测试，再读 diff。顺序反了，容易被实现细节牵着走。

## 按这个顺序看

1. **意图**：这段改动声称解决什么问题？用一句话写下来。写不出来就是还没看懂，别急着给意见。
2. **边界**：空输入、单元素、超大输入、并发、失败路径。挑两个真会发生的说，不要列清单。
3. **副作用**：动了哪个共享状态、谁还在读它、调用方是不是都改了。
4. **收尾**：日志、错误信息、类型标注、文档跟着改了吗。

## 输出

- 按严重程度排：**会坏** > **会咬人** > **读起来费劲**。不要按文件顺序排。
- 每条都说清触发条件；说不出触发条件的是偏好，不是缺陷，标注一下再提。
- 明确写出你没看的部分。审阅的边界，比结论更需要交代。
