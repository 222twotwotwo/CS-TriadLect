# 03 · 20 分钟看懂渲染管线

这一篇讲一件事：**你屏幕上那个画面，是怎么从一堆浮点数和三角形算出来的。**

这个项目里没有 GPU、没有 OpenGL、没有引擎 —— 管线的每一步都是 `core/raster.cpp`
和 `game/shaders/lighting.cpp` 里的普通 C++。所以每一步都能翻到源码看，
而不是"调用一下 API 就出来了"。

管线本身长这样（`core/raster.h` 开头的注释就是这么写的，这里逐段展开）：

```
顶点 → 模型/视图/投影变换 → 近平面裁剪 → 透视除法 → 视口变换
     → tile 分桶 → 多线程扫描转换 → 深度测试 → 逐像素调用着色器 → 色调映射
```

---

## 1. 顶点变换：把"世界里的一个点"变成"屏幕上的一个位置"

模型（一个球、一张桌子）本身存的是**模型空间**的顶点坐标。要走三步：

```
世界坐标 = 模型矩阵 × 顶点        （把桌子摆到房间里的某个位置、转某个角度）
相机坐标 = 视图矩阵 × 世界坐标     （把"相机在哪、朝哪看"折进坐标里）
裁剪坐标 = 投影矩阵 × 相机坐标     （这一步引入了"近大远小"）
```

三个矩阵乘在一起就是常说的 **MVP**。`core/mat.h` 里就是 4×4 矩阵和它们的乘法。

**投影矩阵做了件反直觉的事**：它不直接做透视除法，而是**先把 w 存起来**。
因为除法会丢信息 —— 后面还要用 w 做透视校正插值（见第 5 节）。
这是整个管线里最容易被跳过、又最要紧的一个细节。

## 2. 近平面裁剪：不做的话，画面会炸

相机背后、或者贴在镜头上的三角形，做完透视除法会得到**负数或者天文数字**的坐标 ——
直接画会撕出一整片乱线。

所以每个三角形在进扫描转换之前，先拿近平面切一刀（`raster.cpp` 里的裁剪逻辑）。
切完可能变成 1 个或 2 个三角形。这一步是"必须做对的脏活"，
做错了的症状很典型：**贴近墙壁时画面撕裂**。

## 3. 透视除法 + 视口变换：终于变成像素坐标

```
NDC（归一化设备坐标，x/y/z 都在 [-1,1]）= 裁剪坐标 / w
屏幕像素 = NDC 映射到 [0, 宽度] × [0, 高度]
```

depth（NDC 的 z）会被映射到 `[0,1]`：**0 是近、1 是远** —— 这个方向记住，
下一节要用。

## 4. 分桶：为什么是 32×32 的 tile

`Rasterizer::flush()` 里，屏幕被切成 **32×32 的小块（tile）**，每个三角形按包围盒
丢进它覆盖到的那些桶里。然后开 N 个线程，每个线程**领**（`fetch_add` 原子取）一个
还没人碰的 tile，一直领到没有为止。

这么做的理由：一个三角形的光栅化只影响它自己覆盖的那几十个像素，
线程之间**天然不打架**，不需要加锁保护像素。这是软光栅化能跑出帧率的关键。

代价也真实：**一块被三角形盖满的 tile 很贵，一块空的几乎不要钱** ——
所以帧率取决于"画面里有多少东西"，而不是分辨率那一个数。
（这也是为什么同一个窗口尺寸，站在空走廊和站在满是地砖的屋子前，帧率能差一倍。）

## 5. 透视校正插值：为什么顶点里要存 `invW`

三角形画到屏幕上，每个像素要知道"我在这个三角形里处于什么位置"，
好在上面插值法线、UV、颜色。

**直接在屏幕空间线性插值是错的。** 想象一条向远处延伸的地砖缝：它在屏幕上近处宽、
远处窄，但真实世界里宽度是恒定的。屏幕空间的线性插值会把它插成"近处偏窄、远处偏宽"，
也就是著名的**透视校正**问题 —— 不处理的话，地面纹理会有明显的扭曲。

正解：把属性**先乘上 `1/w`** 再插值，插完**再乘回 `w`**。
`raster_detail::ScreenVertex` 里那个 `invW` 字段就是干这个的，
注释写着"除 invW 外的属性都已经乘过 invW，插值后统一除回来"。

## 6. 扫描转换 + 深度测试：三角形怎么变成像素

`rasterizeTile()` 对每个三角形：

1. 算包围盒，只扫这块区域（不扫全屏）
2. 用重心坐标判断"这个像素在不在三角形里"
3. 在的话，插值出 depth，**和深度缓冲里已有的值比一比**：更近才画

第 3 步就是 **Z-buffer**。它解决的是"哪个面在前面"这个问题 ——
没有它的话，画画的顺序就决定了谁能露出来（画家算法），稍微复杂一点的场景就会穿帮。

深度方向记牢：**0 近 1 远，所以"更小的 depth 更靠前"**。

## 7. 逐像素着色：**这一节就是你要改的地方**

过了深度测试的像素，交给一个函数算颜色：

```cpp
// game/shaders/lighting.cpp
Vec3 shadeSurface(const Surface& surface, const ShadeEnv& env);
```

这个函数是"引擎"和"你要改的着色器"之间**唯一的接口**。
光栅化器把每个像素打包成一个 `Surface`（位置、法线、UV、材质）递进去，
拿回来一个**线性空间的颜色**。GPU 里那个"着色器"，在这里就是一个普通 C++ 函数。

它内部做的是：

| 步骤 | 在算什么 |
|---|---|
| 自发光 `emissive` | 终端屏幕、灯罩 —— 自己就是光源，不受光照影响 |
| 环境光 | `env.ambient × kAmbientStrength`。**第 0 关要改的就是 `kAmbientStrength`** |
| 逐灯累加 | 对每盏灯：漫反射 + 镜面反射（GGX 高光），按**距离平方**衰减 |
| PBR 三件套 | albedo（固有色）/ roughness（粗糙度）/ metallic（金属度）—— **第 2 关在改这三个** |

第 1 关那句"位置比强度重要"，在代码里就是这一行：

```cpp
const float attenuation = light.intensity / (dist2 + light.radius);
```

距离翻一倍，`dist2` 变四倍，亮度就只剩四分之一。所以把灯挪到房间另一头，
再怎么拧强度也救不回来 —— 位置比强度重要，是**平方反比**说的。

## 8. 色调映射：为什么 UI 要写 `2.2` 这种颜色值

画面到这里为止都是**线性空间的 HDR 浮点**：亮度可以远大于 1，
而且不是显示器要的格式。

最后一步在 `core/framebuffer.h` 的 `toRGB8Into()`：

```
曝光 → ACES 色调映射（把 HDR 压进 [0,1]）→ sRGB 传输曲线 → 8 位整数
```

所以你在代码里看到的颜色值是**线性 HDR**的：想要纯白得写 2.0 左右，
字模画红块要写 `{8.0, 0.05, 0.05}` 才能在压完之后还红得刺眼。
这不是随手写的数 —— 是这一条链决定的。

> 附带一个真实的性能教训：`toRGB8Into` 原来每帧新分配一个缓冲、还是单线程，
> 1600×900 上光这一步就要 10ms 以上（每帧 430 万次 `std::pow`）。
> 改成并行 + 复用缓冲之后，同一个尺寸从 20 帧回到 45 帧。
> 渲染管线里"最后那一步"经常被忽略，但它一样是逐像素的。

## 9. 中文字模为什么不走常规路

中文界面在这个项目里是自绘的：`assets/font/pixel12.bin` 是一张**自己烘焙的 1-bit 位图字模**
（17,573 个汉字），C++ 侧直接 `fread` 整个文件 + 二分查找，**不依赖任何图片解码器**。

为什么不用 PNG？因为在这个项目"零第三方依赖"的约束下，读 PNG 就得自己写一个 inflate 解码器 ——
为了字体把复杂度拉满，不值。

失败时的行为也是设计过的：

- 字模**整份**找不到 → 每个字画成**实心红块** + stderr 给出修复命令
- **某个字**不在字模里 → 画**空心方框** + stderr 警告

两种都绝不白屏。最初的方案是"退化到一套内置的 ASCII 5×7 字模"，后来推翻了：
手写的兜底字模平时永远不会被执行到，会悄悄烂掉；而"红块 + 明确的修复命令"
同样满足"绝不白屏"，而且**不可能悄悄失败**。
