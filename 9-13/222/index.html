00

把新 Windows 变成工作台

以下步骤是教程，不会在本机自动安装任何东西。照顺序完成，最后用一组命令确认环境，再进入 Shell、Git 和 C。

还没有自己的电脑？先跳到 05 手机上的 Linux：一台安卓手机装上「小小容器」，就有一台 Debian，GCC、Git、Neovim 一个不少，本页后面的练习在手机上一样能做。等电脑到手，再回来走这一节。

先认识三个窗口

窗口用来做什么
Windows Terminal统一打开 PowerShell、Git Bash、MSYS2 UCRT64 的入口；从 Microsoft Store 安装即可。
PowerShellWindows 的系统终端。安装程序、检查 PATH、启动本站时优先使用它。
Git Bash随 Git for Windows 安装，提供 bash 和常见 Unix 命令；它不是 MSYS2。
MSYS2 UCRT64专门提供 GCC 编译器和类 Unix 工具；编译 C 时使用这个窗口。
不要混淆：Git Bash 主要服务 Git；MSYS2 UCRT64 主要服务 GCC。两者都能输入 ls，但安装目录、包管理器和工具链不是一套。

1. 安装 Git for Windows

下载 64 位安装器，安装时大部分选项保持默认；遇到“默认编辑器”可以选 Neovim，暂时没有 Neovim 就先选 Vim。

安装器里的 PATH 选项保持默认的“Git from the command line and also from 3rd-party software”，这样 PowerShell、编辑器和本站服务都能找到 git。

如果镜像目录有多个版本，选不带 rc（候选版）字样的最新稳定目录；不要下载 MinGit，它没有完整的 Git Bash 体验。

2. 安装 MSYS2，再装 UCRT64 + GCC

MSYS2 是 C 工具链的容器。先下载安装器，再从开始菜单打开 MSYS2 UCRT64，不要在 Git Bash 里执行下面的 pacman 命令。

如果默认源下载慢，在 MSYS2 UCRT64 窗口编辑 /etc/pacman.d/mirrorlist.mingw 与 /etc/pacman.d/mirrorlist.msys，把下面两行放到各自文件最上方：

推荐环境：UCRT64 是 MSYS2 当前推荐的 GCC 环境。它的编译器通常位于 C:\msys64\ucrt64\bin。

3. 让 PowerShell 找到 gcc

在 UCRT64 窗口里输入 which gcc，确认它来自 /ucrt64/bin/gcc。如果希望在 PowerShell、VS Code 和本站真实终端里直接使用 gcc，把 Windows 路径加入“用户 PATH”。

PATH 只改一次：不要把整个 C:\msys64\usr\bin 加进 Windows PATH，也不要把 Git Bash 的 usr\bin 和 UCRT64 的 bin 混在前面，否则可能出现 DLL 或命令版本冲突。

4. 安装 Node.js LTS

本站的 server.cjs 需要 Node.js。下载 Windows x64 的 LTS 安装器，安装时保持默认，并勾选自动加入 PATH。

Node.js 装好后，npm 默认可以访问公网仓库；为减少国内网络波动，把 npm registry 改为 npmmirror：

镜像目录会随 LTS 更新，教程不绑定某个永久版本号；截至 2026 年 9 月，LTS 线为 Node.js 24（Krypton）。

5. 安装 Neovim

优先下载 MSI 安装器；如果下载的是 ZIP，就解压到固定目录，并把包含 nvim.exe 的目录加入用户 PATH。

下载页同时提供 nvim-win64.zip。如果使用 ZIP，建议解压到 C:\Tools\Neovim，并把 C:\Tools\Neovim\bin 加入 PATH；ARM64 电脑选择 nvim-win-arm64.msi。

6. 安装 Bun，并为项目设置镜像

仓库的包管理器是 Bun。Node.js 先装好后，可以用 npm 安装 Bun；Bun 本体下载和 npm registry 是两件事，分别处理。

如果你只学习 cs 这份静态教程，不必安装 Bun；只有要运行根目录的 Vue 招新站时才需要它。项目锁文件是 bun.lock，不要改用 npm 安装。

7. 一次性验收环境

关闭所有旧终端，重新打开 Windows Terminal 的 PowerShell，依次执行。where.exe 用来确认命令实际来自哪里。

判断标准：每条命令都能输出版本号；where.exe gcc 最好指向 C:\msys64\ucrt64\bin\gcc.exe。如果刚改过 PATH，必须关闭并重新打开终端，旧窗口不会自动刷新。

8. 启动这份教程和根项目

cs 是独立静态教学站，根目录则是 Vue + Vite 招新站。两者启动方式不同。

安全边界：cs 页面中的真实终端会在本机执行你输入的命令，并且服务只绑定 127.0.0.1。不要把它部署到公网，也不要在页面终端里执行来源不明的粘贴命令。

02

Git 版本控制

给代码一台时光机：先用 add 与 commit 留下快照，再学会开分支，让没写完的东西不污染主线。

记住三个区域

工作区改文件→ 暂存区git add→ 本地仓库git commit⇄ 远程仓库push / pull

你平时改文件的地方是工作区；git add 把改动放上"打包台"；git commit 才真正生成一个快照。只有 commit 过的东西才被保护。

第一次提交

迷路了就敲 git status。提交信息用"动词 + 内容"：feat: 新功能 · fix: 修 bug · docs: 文档 · refactor: 重构。小步多提交。

编译产物不该进仓库。在根目录写 .gitignore，每行一条：*.o、a.out、node_modules/。

缓冲：分支到底是什么

到这一步，你已经有一条一直在往前长的提交线了：每 commit 一次，线上就多一个点。但麻烦也在这儿——线只有一条。你想大改一版试试看，又怕改坏了回不去；如果还在这唯一的一条线上猛敲 commit，主线就被半成品污染了。

分支（branch）就是给这条线开一个岔路口：从一个提交点再长出第二条线，两条线各自往前走，互不打扰。想试新写法就岔出去，试成了再合回来，试砸了就把那条岔路丢掉，主线一直干净。

关键要记住：分支不是复制一份项目文件夹。它只是一个指向某个提交的名字，新建分支瞬间完成、几乎不占空间；它也不是什么高级技巧，而是日常干活的基本姿势。

你可能以为其实是
分支 = 把项目复制一份只是一个指向某次提交的指针，所以 switch -c 快得没有感觉
main 是特殊的主分支main 只是默认名字，任何分支都能合并、也能删除
切分支只影响 Git 记录切过去之后，磁盘上的文件真的会变成那条线的样子
一句话：commit 是存档点，分支是从某个存档点长出来的平行时间线，switch 就是在时间线之间跳。

git switch：在时间线之间跳

命令作用
git branch列出所有分支，* 标出你在哪条线上
git switch dev切到已经存在的 dev 分支
git switch -c dev新建 dev 并立刻切过去（最常用）
git switch -在最近的两个分支之间来回跳
git merge dev把 dev 合并进当前分支：站在 main 上执行，就是把岔路收进主线
git branch -d dev删掉已经合并完的 dev

亲手验证一次，比看十张图都管用——同一个文件，两个分支，两份内容：

切分支前先把活干完：add + commit。带着没提交的改动切过去，Git 要么把它一起带到新分支、要么直接拒绝切换。
老教程里的 git checkout -b dev 和 git switch -c dev 是同一件事。Git 2.23 之后把 checkout 拆成了两个命令：switch 管换分支，restore 管还原文件，语义更清楚。

远程仓库：把时间线搬到别人的机器上

命令作用
git clone 地址把远端仓库整个拷到本地（自带历史与分支）
git push把本地的提交推到远端
git pull把远端的新提交拉到本地
git log --oneline --graph --all用图形看所有分支的走向，岔路一眼看清

日常循环只有四步：改代码 → add → commit → push。动手前先 pull 一次。用分支干活时多一句：在 dev 上写完、提交完，切回 main，再 git merge dev。

两人改了同一处代码，合并会冲突：文件里出现 <<<<<<< 与 >>>>>>> 标记的两份内容，删掉不要的，再 add + commit。这是常态，不是事故。

04

从 .c 到可执行文件

你写的 C 不是给机器看的。中间隔着四步：预处理 → 编译 → 汇编 → 链接。

点每一步，看发生了什么

平时只需要一条命令

-Wall 打开警告。想看中间产物就用 gcc -E（预处理）、gcc -S（汇编）、gcc -c（目标文件）——每步的产物都是文件，可以任意接续。

报错发生在哪一步

现象阶段与对策
error: expected ';'② 编译：语法错误，看行号，多半是缺分号或括号不配对
undefined reference to `greet'④ 链接：函数没实现，或漏编译某个 .c / 漏链接库
多个源文件一起交给 gcc 就行：gcc main.c util.c -o app。文件多到几十上百个时再上 make / CMake，原理完全一样。
05

没有电脑，手机也是一台 Linux

还没入手电脑也能开工。在安卓手机或平板上装一个「小小容器」（Tiny Container），你会得到一台完整的 Debian：Shell、Git、GCC、Neovim 一个不少，前面几节的练习在手机上同样能做。

原理：这是容器，不是模拟器

小小容器把一整套 Linux（Debian 13 加 XFCE 桌面）打包进一个安卓应用，用 proot 直接在手机上运行里面的程序。不需要 root，不需要刷机：装好打开、等它初始化几分钟，就得到一台能装软件、能上网的 Linux，而且它和 Termux 可以共存、互不干扰。

安卓手机Android 9 以上→ 小小容器 App内置终端→ Debian 容器proot，无需 root→ gcc / git / nvim用 apt 安装
为什么这就够用：你在容器里敲的 ls、gcc、git、nvim，用法和电脑上、服务器上几乎完全一样。真正需要适应的只有外面那层壳——电脑上是 MSYS2 UCRT64，手机上是小小容器。

实质差别只有一处：手机是 ARM64，电脑多半是 x86-64。同一份 hello.c，两边编译出的机器码不同，但源码、命令、输出完全一样——这正好是 04 节那句话的现场演示。

先确认手机能不能用

项目要求
系统版本Android 9（API 28）或更高；iPhone、iPad 不行，这个应用只有安卓版
处理器必须是 arm64。近几年的手机基本都满足；x86 处理器的安卓平板用不了
存储空间中文版安装包约 0.9 GB，装完还要解压出整套系统，建议预留 5 GB 以上
存储权限首次启动会申请；同意后安卓存储会挂载到容器里的 /mnt/sdcard
初始化时间第一次打开要等内容解压，通常几分钟。插着电，别中途退出
它不做什么：不支持 Docker、systemd、chroot，也不是虚拟机（想跑 Windows 软件要另装 Hangover，不是这个方案的强项）。proot 方案本身有性能折扣——单文件练习、刷题、写作业完全够用，但别指望在手机上编译大型项目。

容器里的东西属于“随时可能丢”的一类。养成 02 节的习惯：git commit 之后 git push，代码放到远端，手机丢了也不怕。

下载与安装

下载完允许“安装未知来源的应用”，装好打开，按提示走完初始化，就进入桌面了。

  1. 桌面：XFCE，有文件管理器、浏览器、终端，像一个普通的电脑桌面。
  2. 内置终端：命令行的入口。我们要练的东西都在这里，它和电脑上的终端等价。
  3. 功能 → AVNC：屏幕显示太大或太小，在这里调缩放比例。
应用里已经准备好一批“快速命令”，点一下就自动安装浏览器、输入法、主题这些常用软件，想省事就用它。但下面的开发工具链，建议你自己用 apt 敲一遍——那就是最好的练习。
装第二个容器时必须换一个新代号：代号重复会把旧容器直接覆盖，里面的代码彻底丢失，没有回收站。

把工具链装进容器

打开内置终端（或桌面里的 xfce4-terminal），先看清自己是谁、在哪，再一次装齐编译器、Git 和编辑器。

对照记忆：apt 是 Debian 的包管理器，地位相当于 MSYS2 里的 pacman；build-essential 一次给齐 gcc、g++、make 与标准库头文件，相当于 Windows 上那个 toolchain 包。

默认用户是 tiny，家目录 /home/tiny，sudo 不需要密码（预置容器的登录密码同样是 tiny），所以在这里几乎不用纠结权限问题。

这是便利，不是安全：免密 sudo 加固定密码，是为了让新手少踩坑。别在容器里放真实密码、证件照、网银资料，也别把它当成存放重要文件的主力电脑。

这一步的价值：手机上的代码只有 push 到远端才算真正存下来。容器可以被覆盖、手机可能丢，但 GitHub 上的仓库一直等你——换任何设备，git clone 一条命令就继续干活。

三个最容易踩的坑

编译到一半被系统杀掉：安卓会回收后台进程，长任务被清掉是常态。把小小容器留在前台，并在系统设置里把它加入电池优化白名单，重要编译趁手机电量充足时做。
把容器当成唯一存档：卸载应用、覆盖装容器、系统清理都可能带走数据。凡是舍不得丢的代码，一律 push 到远端。
把它当成过渡方案，而不是替代品：学校机房、图书馆的电脑、同学的电脑都该用起来；课程作业以老师指定的环境为准。好消息是——手机上练出来的手感，在这些地方可以无缝接上。

手机上的 Linux 不是“退而求其次”。它和真正的服务器离得更近：同一套 Shell、同一套 Git、同一个 GCC。先把它用熟，等你拿到自己的电脑时，需要重新学的只剩下安装步骤。

06

学习路线

别贪多。每天 10–20 分钟，两周就能在命令行世界里独立行走。

按这个顺序走

  1. 第 1 周：Shell——把上面九条命令用熟，每天在终端里完成一个真实小任务。
  2. 第 1–2 周：vimtutor 每天 10 分钟，并且强迫自己用 nvim 写代码和笔记。
  3. 第 2 周起：所有作业都 git init，每次改动都提交。
  4. 始终：遇到 bug 先自己查 15 分钟，再去问人。
  5. 没有电脑：按 05 节把环境装进手机，每天的练习照旧——工具是什么不重要，手感才重要。
